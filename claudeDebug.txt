Two bugs, chained. Both confirmed with a minimal reproducer.

Bug 1 — chunked body is declared complete one CRLF too early (this causes the "bad status code")

src/classes/http/HttpRequest.cpp:252-258

if (expectedChunkSize == 0)
{
    buffer.erase(0, expectedChunkSize );   // erases ZERO bytes
    is_complete = true;
    return;
}

The tester (Go client) sends Transfer-Encoding: chunked, never Content-Length — that's why your curl tests pass and the tester fails. A chunked body ends with 0\r\n\r\n. Your code declares the request complete as soon as it sees 0\r\n, and never consumes the final \r\n. Go writes that trailing \r\n in a separate write(), so it usually arrives after you've already answered and called reset().

That orphaned \r\n then becomes the first two bytes of the next request on the keep-alive connection:

raw_buffer = "\r\n" + "POST /post_body HTTP/1.1\r\n..."

parseHeaders (HttpRequest.cpp:133-143) takes everything before the first \r\n as the request line — that's the empty string — methodEnd == npos → throw ERR_NO_METHOD → 400 Bad Request.

This is exactly why POST /post_body with a size of 0 passes and the very next test, size of 100, fails: the size-0 test is the one that leaves the stray CRLF behind.

Also note buffer.erase(0, expectedChunkSize) erases 0 bytes — it should erase the last-chunk line. It's masked today only because resetRequest() clears raw_buffer, but it will corrupt pipelined requests.

Fix: don't set is_complete until the terminator after the 0 line is in the buffer, then erase through it:

if (expectedChunkSize == 0)
{
    size_t endTrailers = buffer.find("\r\n", posEndSize + 2);
    if (endTrailers == string::npos)
        return;                          // wait for more data
    buffer.erase(0, endTrailers + 2);
    is_complete = true;
    return;
}
